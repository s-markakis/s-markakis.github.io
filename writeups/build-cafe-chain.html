This is the Build series' first multi-site design. The earlier eight were one building each; a chain is a different problem — not a bigger network but the same network, eight times, plus a head office that ties them together and a tenth shop that has to come online next month without a van full of engineers.

    
It leans on three ideas that none of the single-site builds needed: write the shop once as a template and stamp it out per site, join the sites with an overlay so every shop talks to HQ and no shop talks to another, and steer the traffic that matters — the tills and the card terminals — onto the reliable link by application, not just by a backup route. That last trio is what the SD-WAN products sell; here we build the mechanics by hand so you can see what they automate.

01

  
The Brief

  
A fictional but very typical Cretan chain: eight shops, a roastery that is also the office, and an owner who wants the ninth open by spring.


  
Each shop is small and the same: two tills with card terminals, a kitchen-display and a menu screen, three or four cameras, a back-office PC, and guest Wi-Fi that people treat like an office. The roastery / HQ holds the central POS and ERP, the loyalty and online-ordering backend, the accounts office, and a small NOC that is supposed to notice a dead shop before the shop phones in. Shops run on whatever the street offers — fibre where it exists, VDSL or 4G where it doesn't — and the card terminals must keep working through a flaky line. A new shop opens every few months, and nobody wants to send an engineer with a laptop each time.


  

    
RequirementWhere it comes from, and what it forces

    
      
R1 Eight shops, one designEach shop must be identical bar a site number, so a fix or a new VLAN rolls out everywhere the same way. A template, not eight hand-built routers.

      
R2 Shops reach HQ, not each otherCentral POS, loyalty, CCTV viewing and config all live at HQ. A compromised shop must not be a path to a sister shop. Hub-spoke, not mesh.

02

  
Four Design Decisions

  
Each is a choice about building a fleet rather than a single site.


  
1 · The shop is a template, not a config

  
Every shop runs the same file; the only thing that changes is a site number. Addresses are 10.<site>.<vlan>.0/24, so site 3's guest network is 10.3.50.0/24 and site 7's is 10.7.50.0/24 — the config computes them from one variable. A new VLAN, a firewall fix, a DNS change: edit the template, re-render, push to all eight. Eight hand-maintained routers drift; one template doesn't.


  
2 · Hub-spoke, because shops have nothing to say to each other

  
A café in Chania never needs to reach a café in Heraklion — only HQ. So the overlay is a hub and spokes: every shop dials one WireGuard tunnel to HQ, and each shop's tunnel is scoped to HQ's addresses only. There is no route from one shop to another, which means a till compromised in one shop is a dead end, not a doorway to the chain.


  
3 · Steer by application, not just by route

  
Plain failover moves everything to the backup when the primary drops. That's not enough here: on a congested fibre line the card terminals can stall long before the line is "down". So the money traffic — tills to the acquirer, and the HQ tunnel — is marked and pinned to the primary with its own tracked route, while guest and bulk traffic are steered separately. This is the one idea that makes "SD-WAN" more than "dual-WAN", and RouterOS does it with mangle marks and routing tables.


  
4 · Opening a shop is plug-and-wait

  
Growth is the point of a chain, so provisioning can't be a bottleneck. A new router ships with a one-line bootstrap: get online, fetch sites/<serial>.rsc from HQ, import it. HQ renders that file from the same template, so the ninth shop is configured identically to the first — no laptop, no SSH session, no chance to fat-finger a VLAN at 7am before opening.

Because a shop's whole estate is one /16, HQ needs exactly one route per shop (10.<s>.0.0/16 down its tunnel), and a shop needs exactly one route to the centre (10.0.0.0/16 up its tunnel). The plan is the routing table.

/interface bridge port add bridge=bridge interface=ether2 frame-types=admit-only-vlan-tagged comment="HQ switch"
/interface bridge vlan add bridge=bridge vlan-ids=20,30,99 tagged=bridge,ether2
/interface vlan
add name=v20-office interface=bridge vlan-id=20
add name=v30-srv interface=bridge vlan-id=30
add name=v99-noc interface=bridge vlan-id=99
/ip address
add address=10.0.20.1/24 interface=v20-office
add address=10.0.30.1/24 interface=v30-srv
add address=10.0.99.1/24 interface=v99-noc
# the overlay head-end: one WireGuard interface, one peer per shop
/interface wireguard add name=wg-hub listen-port=51820
/ip address add address=10.255.0.1/24 interface=wg-hub
# each shop is a peer: its overlay /32 + its whole 10.<id>.0.0/16 behind it
/interface wireguard peers add interface=wg-hub public-key="<shop-03 pubkey>" \
    allowed-address=10.255.0.4/32,10.3.0.0/16 comment="shop-03 Rethymno"
# HQ routes each shop's block back down its tunnel
/ip route add dst-address=10.3.0.0/16 gateway=10.255.0.4


  
HQ is deliberately simple: a server VLAN for the central POS/ERP, loyalty and the NVR; a management VLAN for the NOC; and a single WireGuard interface that is the hub of the star. Every shop is one peer, scoped with allowed-address to its own overlay address plus its /16 — so HQ knows exactly which block sits behind each tunnel, and a shop can't claim another shop's addresses.


  

    Checkpoint: test this before building the next step
    
  • The hub interface is up and listening on 51820; the public endpoint (or dynamic-DNS name) resolves.
  • Once a shop connects, /interface wireguard peers print shows a recent handshake.
  • From HQ you can ping the shop's gateway (10.3.10.1) over the tunnel.

The Overlay: Every Shop Dials HQ

  
One tunnel per shop, up to the hub. Shops reach HQ and central services — and, by design, nothing of each other.

  
▲ Show step 3 in the interactive topology · select SHOP-R1


  
SHOP-R1 — one WireGuard tunnel up to HQ (spoke isolation)
! SHOP-R1 — a DMVPN spoke to the HQ hub. Spokes register with the hub, never each other.
interface Tunnel0
 ip address 10.255.0.4 255.255.255.0
 ip nhrp network-id 1
 ip nhrp nhs 10.255.0.1 nbma hq.cafe.example multicast
 tunnel source GigabitEthernet0/0/0
 tunnel mode gre multipoint
 tunnel protection ipsec profile DMVPN
router eigrp 1
 network 10.255.0.0 0.0.0.255
 network 10.3.0.0 0.0.255.255
! no NHRP shortcut here on purpose — phase-1 hub-spoke, so a shop reaches HQ and central
! services but has no route to a sister shop; the hub is the only meeting point
# SHOP-R1 — one tunnel up to HQ. A shop reaches HQ and central services, never another shop.
/interface wireguard add name=wg-hq listen-port=51820
/interface wireguard peers add interface=wg-hq public-key="<HQ hub pubkey>" \
    endpoint-address=hq.cafe.example endpoint-port=51820 \
    allowed-address=10.0.0.0/16,10.255.0.0/24 persistent-keepalive=25s
/ip address add address=("10.255.0." . ($SITE + 1) . "/24") interface=wg-hq
# central services (POS/ERP/loyalty at HQ) are reached over the tunnel; the default stays local (step 4)
/ip route add dst-address=10.0.0.0/16 gateway=10.255.0.1
# allowed-address scopes the tunnel to HQ's blocks only — there is no route to 10.<other-shop>,
# so a compromised shop cannot reach a sister shop; the hub is the only meeting point


  
This is the heart of hub-spoke. A shop's tunnel is allowed to carry only HQ's 10.0.0.0/16 and the overlay subnet — not 10.<other>.0.0/16. So even though all eight shops terminate on the same hub, no shop has a route to any other. HQ, holding every peer, could route shop-to-shop, but doesn't: the policy matrix (and step 5's firewall) keep the hub a destination, not a transit.


  

    The hub can see everyone — so lock the hub down
    
Hub-spoke isolation lives at the hub. Because HQ terminates every tunnel, a misconfigured HQ firewall (or a compromised HQ) can bridge shops. HQ's own forward rules must permit shop↔HQ only, never shop↔shop, and the hub gets the hardening of the whole chain's crown jewels — it is the one box that, if lost, loses everyone.

  


  

    Checkpoint
    
  • From a shop, you can reach the HQ POS server (10.0.30.10) but a scan of 10.7.0.0/16 (another shop) times out.
  • /ping 10.255.0.1 (the hub) succeeds; the handshake is recent at both ends.
  • Pull the tunnel: central apps fail, but local POS-to-till and guest internet keep working.

  


  
  
09 · Step 4 of 9

  
Dual-WAN & App-Aware Steering

  
Two uplinks, but the card terminals don't just "fail over" — they ride the good link by name, and move only when they have to.

  
▲ Show step 4 in the interactive topology · select SHOP-R1


  
SHOP-R1 — two WANs, steered by application not just by route
! SHOP-R1 — two WANs; PBR pins the card path to WAN1 with a tracked fallback to WAN2.
interface GigabitEthernet0/0/0
 description WAN1 fibre
 ip address dhcp
 ip nat outside
interface Cellular0/1/0
 description WAN2 4G
 ip nat outside
ip sla 1
 icmp-echo 1.1.1.1 source-interface GigabitEthernet0/0/0
 frequency 5
ip sla schedule 1 life forever start-time now
track 1 ip sla 1 reachability
! the money path: tills -> acquirer, pinned to WAN1, falling to 4G if the track drops
ip access-list extended MONEY
 permit tcp 10.3.10.0 0.0.0.255 host <acquirer> eq 443
route-map PBR-MONEY permit 10
 match ip address MONEY
 set ip next-hop verify-availability <wan1-gw> 1 track 1
 set ip next-hop <wan2-gw>
interface Vlan10
 ip policy route-map PBR-MONEY
! everything else: WAN1 primary, WAN2 floating backup
ip route 0.0.0.0 0.0.0.0 dhcp 1 track 1
ip route 0.0.0.0 0.0.0.0 Cellular0/1/0 2
ip nat inside source list NAT-ALL interface GigabitEthernet0/0/0 overload
# SHOP-R1 — two WANs; the money traffic is steered by APPLICATION, not just a backup route.
/interface list add name=WAN
/interface list member
add list=WAN interface=ether1
add list=WAN interface=lte1
/ip dhcp-client add interface=ether1 use-peer-dns=no comment="WAN1 fibre/VDSL"
/ip dhcp-client add interface=lte1 use-peer-dns=no add-default-route=no comment="WAN2 4G"
/ip firewall nat add chain=srcnat action=masquerade out-interface-list=WAN
# mark what MUST take the reliable path: tills, card terminals, and the HQ tunnel
/ip firewall mangle
add chain=prerouting src-address-list=POS dst-address-list=ACQUIRER action=mark-routing new-routing-mark=money passthrough=no
add chain=prerouting out-interface=wg-hq action=mark-routing new-routing-mark=money passthrough=no
# the money mark prefers WAN1, fails to WAN2; the default (guest + bulk) does the same, separately
/ip route add dst-address=0.0.0.0/0 gateway=ether1 routing-mark=money check-gateway=ping distance=1
/ip route add dst-address=0.0.0.0/0 gateway=lte1 routing-mark=money check-gateway=ping distance=2
/ip route add dst-address=0.0.0.0/0 gateway=ether1 check-gateway=ping distance=1
/ip route add dst-address=0.0.0.0/0 gateway=lte1 check-gateway=ping distance=2


  
Two routing tables, one per purpose. Traffic tagged money (tills to the acquirer, and the HQ tunnel) has its own default route that prefers WAN1 and falls to WAN2 on a failed check-gateway ping. Everything else uses the main table, which is steered the same way but independently — so you can, for example, hold guests on WAN1 while pushing the card path to WAN2 during a partial outage, or cap the 4G so a failover doesn't produce a surprise bill. That selectivity — moving an application, not the whole site — is the difference between dual-WAN and SD-WAN.


  

    Metered backup: don't let bulk follow the tills onto 4G
    
When WAN1 drops, the money traffic belongs on 4G — but a shop full of guests streaming does not. Keep the guest/bulk default's failover conservative (or shape it hard on WAN2), or a ten-minute fibre blip becomes a data-cap overage. The point of steering by application is precisely to send the €2 of card traffic over 4G and leave the €200 of video behind.

  


  

    Checkpoint
    
  • A card transaction while WAN1 is up takes WAN1; unplug WAN1 and it moves to 4G within seconds, the sale completing.
  • With WAN1 down, a guest speed test is throttled (or blocked) on 4G while the tills stay responsive.
  • /ip route print where routing-mark=money shows the active gateway following the healthy WAN.

add chain=forward in-interface=v10-pos action=drop log=yes log-prefix=POS-DROP
# cameras record to the HQ NVR over the tunnel; office reaches HQ + internet; guest internet only
add chain=forward in-interface=v40-cctv out-interface=wg-hq dst-address=10.0.30.20 action=accept comment="cameras -> HQ NVR"
add chain=forward in-interface=v50-guest out-interface-list=WAN action=accept comment="guest -> internet only"
add chain=forward in-interface=v20-office action=accept
add chain=forward in-interface=v30-iot out-interface-list=WAN protocol=tcp dst-port=443 action=accept comment="music/KDS cloud"
add chain=forward action=drop log=yes log-prefix=FWD-DROP


  
The payment VLAN is the tightest thing in the shop: it may reach the acquirer on 443 and the HQ POS server over the tunnel, and that is the whole list — not the office PC two metres away, not the internet at large. Guests are the opposite extreme: the internet and nothing else, enforced by sending them straight out the WAN and dropping anything aimed inward. Cameras don't keep footage locally; they stream to the HQ NVR over the tunnel, which also means a shop break-in can't erase the recording.


  

    Checkpoint
    
  • From a till, 443 to the acquirer works and so does the HQ POS; a scan of the office or guest VLAN times out (and lands in POS-DROP).
  • From guest Wi-Fi, nothing on 10.3.0.0/16 or 10.0.0.0/16 answers.
  • The HQ NVR shows the shop's cameras; the shop has no local recorder to lose.

Zero-Touch Provisioning

  
Opening the ninth shop should be: ship a router, plug it in, pour the coffee. No engineer, no laptop.

  
▲ Show step 7 in the interactive topology · select SHOP-R1


  
SHOP-R1 — a new shop self-configures from HQ on first boot
! Cisco's zero-touch is Network Plug-and-Play (PnP): a factory-fresh router finds the PnP server
! (DHCP option 43, DNS, or the cloud redirect) and pulls its config + image with no console session.
pnp profile ztp
 transport https ipv4 pnp.cafe.example port 443
! the per-site config is a template in Cisco DNA Center (or a lightweight PnP server) with the site
! variables — exactly like the rendered .rsc on the MikroTik side. For eight cafés a small PnP server
! is plenty; DNA Center is the product you reach for at hundreds of sites.
# Opening a shop: plug the router in, it fetches its own config from HQ. No truck roll with a laptop.
# the factory/default config carries only a bootstrap WAN DHCP + the provisioning key, then runs ztp:
/system script add name=ztp source={
  :global SITE [/system routerboard get serial-number]
  /tool fetch url=("https://provision.cafe.example/sites/" . $SITE . ".rsc") dst-path=site.rsc
  /import file-name=site.rsc
}
/system scheduler add name=firstboot start-time=startup interval=0 on-event=ztp
# HQ renders sites/<serial>.rsc from the ONE template + that site's variables (SITE id, keys, WAN type)
# opening shop #9 is: ship a pre-keyed router, staff plug it in, it joins the overlay in minutes


  
Zero-touch turns a site opening from an engineering visit into a logistics task. The router ships with a one-screen default: come up on WAN DHCP, reach the provisioning server, pull sites/<serial>.rsc, import it, reboot into the real config. HQ generates that file from the same template every other shop uses — so the ninth shop is, byte for byte, configured like the first. The serial number (or a QR sticker scanned at HQ when the box is keyed) is the only thing that ties a physical router to a site.


  

    Bootstrap trust is the whole game
    
The dangerous moment is first boot, before the tunnel exists: the router fetches config over the open internet. Serve the provisioning file over HTTPS with a pinned CA, key each router at HQ (so a stolen serial can't pull a config), and make the provisioning server refuse a serial that's already claimed. Get this wrong and "zero-touch" becomes "anyone-touch".

  


  

    Checkpoint
    
  • A factory-reset router with the default config boots, fetches its .rsc, and comes up fully configured with its tunnel to HQ.
  • HQ's provisioning log shows the serial being served once; a second request for the same serial is refused.
  • The resulting config is identical to a hand-stamped one for that site (diff them).

Management only happens from the NOC, over the tunnel — the shops expose nothing to the street. The card path keeps the discipline PCI expects: its own VLAN from till to acquirer, logged at the drop, and never co-mingled with guest or office traffic — the segmentation isn't a nicety, it's what keeps the chain's card handling in scope-control.

Residual Risk

  
What the network can't do on its own, and what covers each gap.


  
    
    
  • The hub is the single point of everything. Lose HQ and every shop loses central services (local POS keeps working, but loyalty, reporting and CCTV viewing stop). HQ needs a redundant head-end (a second WireGuard endpoint the shops also hold) and real backups — it is the crown jewels.
    • 
    
  • The payment application, not the network. Segmentation keeps the card path isolated, but the acquirer integration, the terminals' own firmware and the PCI paperwork are the merchant's responsibility. The network puts the card path in scope-control; it doesn't make the chain compliant by itself.
    • 
    
  • Provisioning trust. Zero-touch is only as safe as the bootstrap. A leaked provisioning URL or an unpinned CA turns "plug it in" into "anyone can pull a shop's config". Per-router keys and a claim-once server are the controls.
    • 
    
  • Shop physical security. A router behind the counter is reachable by a determined person. Lockable enclosures, disabled unused ports, and management only over the tunnel mean a plugged-in laptop lands nowhere — but the box itself should be out of reach.
    • 
    
  • Template blast radius. One template is the strength and the danger: a bad push hits all eight shops at once. Stage changes to one shop, verify, then roll the fleet — and keep the one-command rollback honest.
    •

The Attacker's View

  
I test networks like this for a living. On a chain the prize is the card data and the hub — here's what I'd try, and why each stays bounded.


  
    
    
  • Pop one shop, pivot to the others. The obvious chain attack — own a till in Chania, walk to Heraklion. But a shop's tunnel is scoped to HQ only; there is no route to a sister shop, so a compromised shop is an island with a single door, and that door leads to the hub's firewall, not to the fleet.
    • 
    
  • Sit on the guest Wi-Fi and reach the tills. Guest is forwarded straight to the WAN and dropped inward; from a café table a scan of the shop's own VLANs and of HQ returns nothing. The payment VLAN doesn't answer the office two metres away, let alone a guest.
    • 
    
  • Grab the card traffic in flight. The tills talk TLS to the acquirer and ride a scoped path; the interesting target is the terminal and the acquirer integration, not the wire. The network keeps the card path on its own segment end to end so there's nothing to sniff from an adjacent VLAN.
    • 
    
  • Impersonate a new shop at provisioning. Zero-touch is the soft spot: fetch a config before the tunnel exists. So I'd try a guessed serial against the provisioning server — which refuses an unknown or already-claimed serial and serves only over a pinned HTTPS, so a guess returns nothing useful.
    • 
    
  • Go for the hub. The efficient attack skips the shops entirely and targets HQ, because the hub can reach everyone. That's exactly why the design treats HQ as the crown jewels: it is the one box that is hardened, MFA'd, backed up and watched hardest — compromising a shop is noise; compromising the hub is the whole chain, and it's the thing defended accordingly.
    •

Appendix

  
The Same Design on Cisco

  
Most of this maps to IOS; one word of honesty about "SD-WAN".


  
The shop and HQ routers become ISRs (a C1121X per shop, a C8300 at HQ); VLANs and SVIs, DHCP, the Zone-Based Firewall and the QoS (MQC with a priority class for the tills) all have direct equivalents. The overlay is DMVPN (a hub-spoke design by nature) or FlexVPN, and app-aware steering is PBR with tracked next-hops — the same mechanics by different names.


  

    "SD-WAN" the product vs the mechanism
    
Real Cisco SD-WAN is Catalyst SD-WAN (Viptela) with vManage — a controller that automates exactly what we built by hand: the overlay, the per-application policy, and zero-touch onboarding through PnP. For eight cafés the DIY DMVPN + PBR approach is the right size and cost; vManage (or Meraki, or a Fortinet/VeloCloud fabric) earns its licensing when the fleet is hundreds of sites and the policy changes weekly. This build teaches the mechanics those products package; knowing them is how you tell whether you need the product.

  1. Write the site once as a template. One variable per site; eight identical shops that can't drift.

  4. Make opening a shop plug-and-wait. Zero-touch from HQ — and treat the bootstrap as the security boundary it is.
