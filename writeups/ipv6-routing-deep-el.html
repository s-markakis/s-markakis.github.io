IPv6 σε Βαθος
OSPFv3, /127 Links και BGP

Η δρομολόγηση v6 μοιάζει με δρομολόγηση v4 με μεγαλύτερους αριθμούς, μέχρι τη στιγμή που ένα router-ID δεν ανεβαίνει, μια αλλαγή prefix δεν προκαλεί SPF, ή το BGP session σου γίνεται Established και ο ISP πετάει κάθε prefix που στέλνεις. Αυτό είναι το κομμάτι που διαφέρει πραγματικά, ρυθμισμένο σε RouterOS 7 και IOS-XE δίπλα-δίπλα.

IPv6 OSPFv3 BGP RFC 6164 Multihoming RouterOS Cisco IOS

Τα περισσότερα που ξέρεις για OSPF και BGP μεταφέρονται. Οι διαφορές μαζεύονται σε τρία σημεία. Το OSPFv3 ξεχωρίζει την τοπολογία από τη διευθυνσιοδότηση. Τα point-to-point links έχουν δικούς τους κανόνες διευθυνσιοδότησης. Και το IPv6 multihoming έχει ένα πρόβλημα aggregation που το IPv4 το σκέπαζε με NAT. Το καθένα από αυτά σου χαρίζει ένα κλασικό απόγευμα «είναι ρυθμισμένο, γιατί δεν δουλεύει».

01

Τι Αλλαξε Πραγματικα στο OSPFv3

Ίδιο SPF, ίδιες areas, ίδιες καταστάσεις adjacency. Τα LSAs ξαναχτίστηκαν ώστε τοπολογία και prefixes να ταξιδεύουν χωριστά.

Οι πρακτικές συνέπειες:

  • Τα adjacencies δεν νοιάζονται για subnets. Το OSPFv3 τρέχει ανά link, μεταξύ link-local διευθύνσεων. Δύο routers στο ίδιο segment γίνονται γείτονες ακόμα κι αν τα global prefixes τους δεν ταιριάζουν. Στο v2 αυτή η ασυμφωνία θα σταματούσε το adjacency, οπότε το παλιό βήμα «έλεγξε τη μάσκα» εδώ δεν πιάνει τίποτα.
  • Το router-ID είναι ακόμα αριθμός 32 bit, και στο IOS παίρνεται ακόμα από μια IPv4 διεύθυνση by default. Ένας router μόνο με v6, χωρίς IPv4 διεύθυνση, δεν έχει router-ID, και το OSPFv3 δεν ξεκινά μέχρι να του ορίσεις ένα. Όρισέ το ρητά παντού.
  • Τα next hops είναι link-local. Έρχονται από το Link LSA. Ένα show ipv6 route ospf γεμάτο FE80:: next hops είναι σωστό, και γι' αυτό η αλλαγή του global prefix ενός link δεν ενοχλεί το forwarding.
  • Το authentication μετακόμισε. Το OSPFv3 άφησε το ενσωματωμένο auth του v2 για χάρη του IPsec (RFC 4552). Αργότερα προστέθηκε το Authentication Trailer (RFC 7166). Areas με διαφορετικούς κατασκευαστές αποτυγχάνουν όταν η μία πλευρά χρησιμοποιεί IPsec και η άλλη το trailer, οπότε συμφωνήστε στον μηχανισμό πριν κατηγορήσετε τα κλειδιά.
RouterOS 7 — OSPFv3 σε point-to-point uplink
/routing ospf instance add name=v3 version=3 router-id=10.255.0.1 \
    redistribute=connected
/routing ospf area add name=bb-v3 area-id=0.0.0.0 instance=v3
/routing ospf interface-template add area=bb-v3 interfaces=ether2 type=ptp
/routing ospf interface-template add area=bb-v3 interfaces=loopback passive
# "loopback" = ένα άδειο bridge με το /128 του router
/routing ospf neighbor print        # state=Full, address=fe80::...
/routing ospf lsa print where instance=v3
IOS-XE — OSPFv3 σε address-family mode
R2(config)# router ospfv3 1
R2(config-router)# router-id 10.255.0.2
R2(config-router)# address-family ipv6 unicast
R2(config-router-af)# passive-interface Loopback0
R2(config-router-af)# exit-address-family
R2(config)# interface GigabitEthernet0/0/0
R2(config-if)# ospfv3 1 ipv6 area 0
R2(config-if)# ospfv3 network point-to-point
R2# show ospfv3 neighbor
R2# show ospfv3 database link     # τύπος 8: link-local + prefixes κάθε γείτονα
R2# show ospfv3 database prefix   # τύπος 9: πού δρομολογεί η area

Η ίδια διεργασία router ospfv3 μπορεί να κουβαλήσει και IPv4 (address-family ipv4 unicast, RFC 5838). Κάθε address family χρησιμοποιεί δικό της εύρος instance-ID στο σύρμα: 0–31 για IPv6 unicast, 64–95 για IPv4 unicast. Δύο routers με την ίδια area και διαφορετικό instance ID δεν σχηματίζουν adjacency, και τίποτα στα logs δεν λέει γιατί. Όταν ανακατεύεις AF-mode και παλιό OSPFv3 config, έλεγξε πρώτα το instance ID.

02

Point-to-Point Links: /127, Οχι /64

Το «κάθε subnet είναι /64» ισχύει για τα LAN και είναι λάθος για τα links από router σε router. Το RFC 6164 εξηγεί γιατί.

Ένα /64 σε link με ακριβώς δύο routers αφήνει 264 διευθύνσεις που δεν υπάρχουν. Όταν φτάνει πακέτο για μία από αυτές, ο router ξεκινά επίλυση γείτονα και κρατά μια incomplete εγγραφή όσο περιμένει. Αρκετές τέτοιες, από έναν host που φέρεται άσχημα ή από σκόπιμη κίνηση, μπορούν να γεμίσουν το neighbor cache και να διώξουν τις πραγματικές εγγραφές. Σε ένα LAN το περιορίζεις με όρια στο cache. Σε ένα p2p link το εξαφανίζεις με ένα prefix χωρίς άδειες διευθύνσεις:

Σχεδιο διευθυνσεων: κρατα ενα /64 ανα link, ρυθμισε το /127
reserved   2001:db8:acad:ff01::/64     # κρατά το σχέδιο ευθυγραμμισμένο σε nibbles και αφήνει χώρο για αλλαγές
configured 2001:db8:acad:ff01::a/127   # R1
           2001:db8:acad:ff01::b/127   # R2  (τα a και b διαφέρουν μόνο στο τελευταίο bit)

# RouterOS 7
/ipv6 address add interface=ether2 address=2001:db8:acad:ff01::a/127 advertise=no
# IOS-XE
R2(config-if)# ipv6 address 2001:db8:acad:ff01::b/127

Πρόσεξε το advertise=no στο RouterOS: το SLAAC θέλει /64, οπότε RAs σε /127 δεν έχουν νόημα, και δεν θέλεις ένα link μεταξύ routers να διαφημίζεται ως default gateway.

💡 Βαλε Οριο στο Neighbor Cache και στα LAN

Τα LAN πρέπει να μείνουν /64, οπότε εκεί η άμυνα είναι ένα ταβάνι. RouterOS: /ipv6 settings set max-neighbor-entries=8192 (ανάλογα με το μέγεθος του segment). IOS: ipv6 nd cache interface-limit 2000 ανά interface. Συνδύασέ το με το inbound default-deny από το Μέρος 3: η αυθόρμητη κίνηση από το internet προς τυχαίες διευθύνσεις μέσα στα /64 σου πετιέται πριν ο router ξεκινήσει καν επίλυση γείτονα γι' αυτήν.

Η αλλη επιλογη: μονο link-local (RFC 7404)

Το OSPFv3 και το BGP μπορούν και τα δύο να τρέξουν σε links χωρίς καμία global διεύθυνση, γιατί το adjacency και το next hop είναι ήδη link-local. Γλιτώνεις χώρο διευθύνσεων και τα links δεν μπορούν να στοχευτούν από έξω. Το πληρώνεις στο troubleshooting: δεν μπορείς να κάνεις ping ένα interface από απομακρυσμένο δίκτυο, και τα hops του traceroute δείχνουν όποια global διεύθυνση διαλέξει ο router ως source για το ICMP error, συνήθως ένα loopback. Για ένα μικρό δίκτυο με λίγα links, το /127 είναι πιο εύκολο στη λειτουργία. Το μόνο-link-local αξίζει σε μεγάλα fabrics.

03

Και τα Static Routes Θελουν Link-Local

Ένα link-local next hop έχει νόημα μόνο μαζί με το interface του, οπότε το interface είναι μέρος του route.

Default route προς τον ISP μεσω της link-local διευθυνσης του
# RouterOS 7 — το %interface ορίζει σε ποιο link ανήκει η link-local
/ipv6 route add dst-address=::/0 gateway=fe80::1%pppoe-out1

# IOS-XE — interface + link-local· ένα global next hop σκέτο δουλεύει επίσης
R1(config)# ipv6 route ::/0 GigabitEthernet0/0/0 FE80::1

Κάθε interface έχει ένα fe80::/64, οπότε το fe80::1 σκέτο είναι διφορούμενο. Χωρίς το interface το route είτε δεν μπαίνει είτε λύνεται στο λάθος link. Το κέρδος είναι ότι το route αντέχει κάθε renumbering των global prefixes.

04

Multihoming και BGP: το Προβλημα του Aggregation

Με το IPv4 έκανες NAT πίσω από δύο ISP και τελείωνες. Με το IPv6 πρέπει να αποφασίσεις από πού έρχονται οι διευθύνσεις σου.

ΠροσεγγισηΠως δουλευειΤο αγκαθι
PI /48 + BGPΔικό σου provider-independent /48 από το RIR (εδώ το RIPE NCC), που το ανακοινώνεις και στους δύο ISPΧρειάζεται αριθμό AS, μέλος RIR ή sponsoring LIR, και ISP που δέχονται BGP από σένα. Η πραγματική λύση, αν πληροίς τις προϋποθέσεις.
Δύο PA prefixes στο LANΚάνουν delegate και οι δύο ISP· ο router διαφημίζει και τα δύο στα RAs· οι hosts παίρνουν δύο διευθύνσειςΟ host διαλέγει source διεύθυνση και ο router διαλέγει έξοδο. Κίνηση με source το prefix του ISP A που βγαίνει από τον ISP B πετιέται από τα anti-spoofing filters του B. Χρειάζεσαι source-based routing στον router.
NPTv6 (RFC 6296)Οι hosts χρησιμοποιούν ένα εσωτερικό prefix· ο router κάνει stateless 1:1 αλλαγή prefix ανά έξοδοΠειραματικό RFC, σπάει πρωτόκολλα που κουβαλάνε διευθύνσεις, και δεν σου δίνει καμία ασφάλεια. Λειτουργικός συμβιβασμός μόνο όταν δεν ταιριάζει κανένα από τα παραπάνω.

Ο κανόνας μεγέθους είναι αυτός που πρέπει να θυμάσαι: ο παγκόσμιος πίνακας γενικά δεν δέχεται τίποτα μακρύτερο από /48 για IPv6. Ένα /56 από τον ISP σου δεν είναι δικό σου για να το ανακοινώσεις αλλού. Ένα PI /48 είναι. Φτιάξε ROA για αυτό πριν από την πρώτη ανακοίνωση, γιατί τα upstreams που κάνουν RPKI validation πετάνε μια ανακοίνωση χωρίς αντίστοιχο ROA.

IOS-XE — ανακοινωσε ενα PI /48, δεξου μονο default
ipv6 route 2001:db8:5000::/48 Null0           ! άγκυρα ώστε να ταιριάζει το network statement
ipv6 prefix-list V6-OUT seq 5 permit 2001:db8:5000::/48
ipv6 prefix-list V6-IN  seq 5 permit ::/0
!
router bgp 65010
 bgp router-id 10.255.0.2
 no bgp default ipv4-unicast
 neighbor 2001:db8:b::1 remote-as 64501
 address-family ipv6 unicast
  network 2001:db8:5000::/48
  neighbor 2001:db8:b::1 activate
  neighbor 2001:db8:b::1 prefix-list V6-OUT out
  neighbor 2001:db8:b::1 prefix-list V6-IN in
 exit-address-family
RouterOS 7 — το ιδιο session
/ipv6 route add dst-address=2001:db8:5000::/48 blackhole
/ipv6 firewall address-list add list=bgp-out address=2001:db8:5000::/48
/routing filter rule add chain=isp-in rule="if (dst == ::/0) { accept } else { reject }"
/routing bgp connection add name=isp-b as=65010 router-id=10.255.0.1 \
    remote.address=2001:db8:b::1 remote.as=64501 local.role=ebgp \
    address-families=ipv6 output.network=bgp-out input.filter=isp-in
/routing bgp session print
⚠ Παγιδα — IPv6 Routes πανω απο IPv4 Session

Το BGP μπορεί να κουβαλήσει IPv6 prefixes πάνω από session μεταξύ IPv4 διευθύνσεων (MP-BGP), και πολλοί το στήνουν έτσι για να ξαναχρησιμοποιήσουν ένα υπάρχον peering. Τότε το next hop κωδικοποιείται ως IPv4-mapped διεύθυνση (::ffff:192.0.2.1), που δεν είναι προσβάσιμη στον πίνακα v6. Το session ανεβαίνει και τα prefixes έρχονται, αλλά είναι άχρηστα ή φιλτράρονται. Είτε κάνε peering με IPv6 διευθύνσεις για την οικογένεια IPv6 (το πιο καθαρό), είτε όρισε v6 next hop με outbound route-map. Στο IOS, έλεγξε επίσης το no bgp default ipv4-unicast μαζί με ρητό activate σε κάθε address family. Χωρίς αυτά, το IOS ενεργοποιεί τον γείτονα για IPv4 by default, και η οικογένεια IPv6 μένει βουβή.

Βασικα Συμπερασματα

  1. Το OSPFv3 χωρίζει την τοπολογία από τα prefixes. Τα Router/Network LSAs δεν έχουν διευθύνσεις. Τις κουβαλάνε τα Link (τύπος 8) και Intra-Area-Prefix (τύπος 9) LSAs, οπότε οι αλλαγές prefix δεν προκαλούν πλήρες SPF.
  2. Τα adjacencies σχηματίζονται πάνω από link-local, ανά link. Οι ασυμφωνίες subnet δεν τα εμποδίζουν. Οι ασυμφωνίες instance-ID ναι.
  3. Όρισε ρητά το router-ID των 32 bit. Ένας router μόνο με v6 δεν έχει IPv4 διεύθυνση να το δανειστεί.
  4. /127 στα links μεταξύ routers (RFC 6164), από ένα δεσμευμένο /64, με τα RAs κλειστά. Κράτα τα LAN σε /64 και βάλε όριο στο neighbor cache.
  5. Τα link-local next hops θέλουν το interface τους: fe80::1%pppoe-out1 ή Gi0/0/0 FE80::1.
  6. Το IPv6 multihoming σημαίνει PI /48 + BGP, ή δρομολόγηση με βάση το source πάνω σε δύο PA prefixes. Ένα delegated /56 δεν ανακοινώνεται σε δεύτερο ISP. Δημοσίευσε ROA πριν την ανακοίνωση.
  7. Peering v6 πάνω από v6. Το v6 NLRI πάνω από v4 session παίρνει IPv4-mapped next hop.
