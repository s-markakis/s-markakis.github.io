Surgery on a Running Network
RouterOS 6 to 7

RouterOS 7 is not a service-pack bump on 6 — it is a major version with changes that do not all migrate themselves. Upgrade a production router blind and you can come back to a box that boots fine but has no Wi-Fi, no VPN, or a firewall that behaves differently than it did. The upgrade itself is one command; doing it safely on a live box is about knowing what breaks, having a way back in, and a tested rollback.

Surgery Migration RouterOS 7 Upgrade wifi package Rollback

Most RouterOS upgrades are boring — a patch within a branch, reboot, done. The jump from the 6.x branch to 7.x is not that. Whole subsystems were re-architected, and the critical fact for a live upgrade is that some of them do not carry your configuration across automatically. The box will boot, management will come back, and a subsystem you depend on may simply be gone or behaving differently.

So this is a planned-change post, not a “click upgrade” one. The method: know exactly which subsystems break, upgrade with a way back in that does not depend on the thing you are changing, verify each subsystem against a checklist, and have a rollback you have actually tested — because the one upgrade that goes wrong is the one where you assumed it would not.

01

What Actually Breaks

Four subsystems change enough to matter. The wireless one is the trap, because it does not auto-convert and the box boots happily without it.

SubsystemWhat changes
Wireless → wifiThe old /interface wireless is replaced by the wifi package. Config does not auto-migrate — rebuild SSIDs/CAPsMAN. On some hardware the right package must be installed.
WireGuardNew in 7 (/interface wireguard) — a gain, not a break, but any v6-era VPN workaround should be reconsidered.
QueuesQueue internals and CAKE/FQ behaviour changed; re-test shaping rather than assume identical numbers.
Firewall / defaultsMostly compatible, but the default config and a few defaults differ — verify, do not assume.

02

The Upgrade, In Order

Back up two ways, upgrade with a way back in, verify per subsystem, and know your rollback before you start.

StepDoRollback
1 · Back up both waysBinary /system backup (restores only on the same version) and a text /export (human-readable, portable). Copy both off the box.—
2 · Secure a way inConsole/OOB access that does not depend on Wi-Fi or the VPN you are about to change. Never upgrade Wi-Fi over Wi-Fi.—
3 · Upgrade RouterOSMove to the latest 6.x long-term first if far behind, then to 7.x; reboot.Downgrade to the saved 6.x package (/system package downgrade).
4 · Upgrade RouterBOOT/system routerboard upgrade + reboot — firmware, separate from the OS.— (rarely reverted).
5 · Verify per subsystemRouting, firewall, NAT, DHCP, VPN, and Wi-Fi — against the checklist, not by vibes.Downgrade if a subsystem cannot be restored.
6 · Rebuild Wi-FiRecreate the wifi/CAPsMAN config (it did not come across). Confirm clients associate.Downgrade to 6.x where the old wireless config still exists.
⚠ Gotcha — the export that will not import, and upgrading Wi-Fi over Wi-Fi

Two ways people get stranded. First, a text /export from a 6.x box contains /interface wireless stanzas that do not exist on 7 — pasting it back fails on those lines, so do not treat the export as a clean restore for wireless; rebuild that section by hand. Second, never run the upgrade while your only access is the Wi-Fi or VPN that the upgrade changes — you will lose the session mid-flight and be locked out. Console or a wired management path that survives the change is non-negotiable here.

Takeaways

  1. 6 to 7 is a major version, not a patch — some subsystems do not carry your config across.
  2. Wireless becomes the wifi package and does not auto-convert — the box boots with no Wi-Fi until you rebuild it.
  3. Back up both ways — binary (version-locked) and text export (portable, but not wireless-clean).
  4. Never upgrade Wi-Fi over Wi-Fi, or a VPN over that VPN — keep a console/OOB path that survives the change.
  5. Have a tested downgrade to 6.x staged before you start — the rollback you never tested is not a rollback.

Sitting on RouterOS 6 because 7 feels risky?

The RouterOS 6-to-7 jump is safe when you know which subsystems do not auto-migrate and you keep a way in and a way back. I plan and run the upgrade on live MikroTik fleets with out-of-band access and a tested downgrade.
