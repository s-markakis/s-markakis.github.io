IPv6 σε Βαθος
Το Firewall, Σωστα

Το «επίτρεψε το ICMPv6» είναι σωστό αντανακλαστικό, αλλά σε λάθος επίπεδο λεπτομέρειας. Το RFC 4890 χωρίζει κάθε τύπο ICMPv6 σε πρέπει-να-περάσει, καλό-να-περάσει, μόνο-τοπικό και ασφαλές-να-πεταχτεί, και αντιμετωπίζει διαφορετικά την κίνηση προς τον router από την κίνηση μέσα από αυτόν. Εδώ γίνεται πλήρη rulesets που μπορείς να επικολλήσεις, μαζί με προστασία first-hop και έναν τρόπο να αποδείξεις ότι v4 και v6 εκθέτουν τα ίδια.

IPv6 Firewall RFC 4890 ICMPv6 RA Guard RouterOS Cisco IOS

Ένα IPv6 edge firewall κάνει την ίδια δουλειά με ένα v4: επιτρέπει ό,τι ξεκίνησε το εσωτερικό, απορρίπτει ό,τι ξεκινά το εξωτερικό, προστατεύει τον ίδιο τον router. Δύο πράγματα αλλάζουν. Πρώτον, τίποτα δεν κρύβεται πίσω από NAT, οπότε το firewall είναι ο μόνος έλεγχος ανάμεσα στο internet και σε κάθε host. Δεύτερον, το πρωτόκολλο στηρίζεται στο ICMPv6 για πράγματα που το IPv4 έκανε αλλιώς: επίλυση διευθύνσεων, ανακάλυψη router και path MTU. Πέτα λάθος τύπο ICMPv6 και το v6 χαλάει. Επίτρεψε λάθος τύπο και ανοίγεις κάτι που δεν ήθελες.

Η θεραπεία και για τα δύο είναι το RFC 4890. Είναι σύντομο, συγκεκριμένο, και σχεδόν κανείς δεν το διαβάζει. Αυτό το post το μετατρέπει σε κανόνες.

01

Το RFC 4890 σε Πινακα

Μετράνε δύο στήλες: κίνηση προς τον router (input) και κίνηση μέσα από αυτόν (forward). Δεν παίρνουν την ίδια απάντηση.

Τυπος ICMPv6Μεσα απο τον router (forward)Προς τον router (input)
1 Dest. UnreachableΠρέπει να περνά (όλοι οι κωδικοί)Πρέπει να γίνεται δεκτό
2 Packet Too BigΠρέπει να περνά, αλλιώς το PMTUD εξαφανίζει τα μεγάλα πακέταΠρέπει να γίνεται δεκτό
3 Time ExceededΟ κωδικός 0 πρέπει να περνά· ο 1 καλό είναιΠρέπει να γίνεται δεκτό
4 Parameter ProblemΟι κωδικοί 1–2 πρέπει να περνούν· ο 0 καλό είναιΠρέπει να γίνεται δεκτό
128/129 EchoΣτη λίστα «να μην πετιέται» (έλεγχοι συνδεσιμότητας, Teredo). Το inbound echo-request προς hosts μένει θέμα πολιτικής, οπότε βάλε όριο.Δεκτό, με όριο ρυθμού
130–132, 143 MLDLink-local, δεν προωθείται ποτέΠρέπει να γίνεται δεκτό (το multicast και το snooping εξαρτώνται από αυτό)
133–136 NDPLink-local, δεν προωθείται ποτέΠρέπει να γίνεται δεκτό (μόνο με hop limit 255)
137 RedirectΔεν προωθείται ποτέΔεκτό, ή κλείσε τα redirects
138 Router RenumberingDropDrop: αλλάζει τη ρύθμιση των routers
139/140 Node Info, πειραματικά, μη ανατεθειμέναDropDrop

Δύο πρακτικές σημειώσεις. Σε stateful firewall, τα errors που ανήκουν σε ροή που παρακολουθείται (ένα Packet Too Big για το εξερχόμενο TCP session σου) χαρακτηρίζονται related και περνούν ούτως ή άλλως από τον κανόνα established/related. Τα ρητά accepts για τους τύπους 1–4 καλύπτουν όσα χάνει το conntrack: ασύμμετρα paths, μια ροή που έζησε περισσότερο από την εγγραφή της στο conntrack, ένα reboot. Και το «δεν προωθείται ποτέ» για το NDP το επιβάλλει το ίδιο το πρωτόκολλο (link-local εμβέλεια, hop limit 255), οπότε στο forward chain δεν χρειάζεσαι καθόλου κανόνες γι' αυτά.

INPUT — προστασια του ιδιου του router
/ipv6 firewall filter
add chain=input action=accept connection-state=established,related,untracked
add chain=input action=drop connection-state=invalid
add chain=input action=drop protocol=icmpv6 icmp-options=138:0-255 \
    comment="RFC 4890: router renumbering"
add chain=input action=accept protocol=icmpv6 \
    comment="NDP, MLD, errors, echo"
add chain=input action=accept protocol=udp dst-port=546 src-address=fe80::/10 \
    in-interface-list=WAN comment="DHCPv6-PD replies (Part 2)"
add chain=input action=accept protocol=udp dst-port=53 in-interface-list=LAN \
    comment="router as DNS resolver for the LAN, if you use it"
add chain=input action=accept protocol=tcp dst-port=53 in-interface-list=LAN
add chain=input action=accept in-interface-list=MGMT
add chain=input action=drop log=yes log-prefix="v6-in-drop"
FORWARD — οτι διασχιζει τον router
add chain=forward action=accept connection-state=established,related,untracked
add chain=forward action=drop connection-state=invalid
add chain=forward action=drop src-address-list=bad_ipv6
add chain=forward action=drop dst-address-list=bad_ipv6
add chain=forward action=drop in-interface-list=WAN src-address=fc00::/7 \
    comment="ULA never arrives from the internet"
# errors που πρέπει να περνούν κατά RFC 4890 (για ροές που έχασε το conntrack)
add chain=forward action=accept protocol=icmpv6 icmp-options=1:0-255
add chain=forward action=accept protocol=icmpv6 icmp-options=2:0-255
add chain=forward action=accept protocol=icmpv6 icmp-options=3:0-1
add chain=forward action=accept protocol=icmpv6 icmp-options=4:0-2
# echo: θέμα πολιτικής· βάλε όριο στο inbound ώστε να μη φορτώνει τους hosts
add chain=forward action=accept protocol=icmpv6 icmp-options=128:0 \
    limit=10,20:packet
# η πραγματική πολιτική
add chain=forward action=accept in-interface-list=LAN out-interface-list=WAN
add chain=forward action=drop log=yes log-prefix="v6-fwd-drop" \
    comment="default deny: inbound from WAN, and LAN-to-LAN unless allowed above"
⚠ Παγιδα — Ισοδυναμια Σημαινει και LAN-προς-LAN

Τα περισσότερα v4 rulesets μπλοκάρουν την κίνηση μεταξύ VLAN (guest προς προσωπικό, IoT προς servers) στο forward chain. Στο v6 οι ίδιοι hosts έχουν πια δεύτερο σετ διευθύνσεων, και αν το v6 forward chain τελειώνει με «LAN προς οπουδήποτε: accept», η κατάτμησή σου υπάρχει μόνο στο IPv4. Το ruleset πιο πάνω επιτρέπει μόνο LAN → WAN. Πρόσθεσε ρητά accepts μεταξύ VLAN με ζεύγη in-interface/out-interface, τα ίδια που έχει το v4. Φίλτραρε με interface και όχι με διεύθυνση, γιατί οι διευθύνσεις είναι delegated και θα αλλάξουν (Μέρος 2).

03

Η Εκδοχη για IOS — Zone-Based

Το ZBF κάνει inspect σε v4 και v6 με την ίδια πολιτική. Οι παγίδες είναι το self zone και τα ACLs που βιδώνει ο κόσμος δίπλα του.

IOS / IOS-XE — inspect απο μεσα προς τα εξω, απορριψη απο εξω προς τα μεσα
zone security INSIDE
zone security OUTSIDE
!
class-map type inspect match-any C-OUTBOUND
 match protocol tcp
 match protocol udp
 match protocol icmp
!
policy-map type inspect P-IN-TO-OUT
 class type inspect C-OUTBOUND
  inspect
 class class-default
  drop log
!
zone-pair security ZP-IN-OUT source INSIDE destination OUTSIDE
 service-policy type inspect P-IN-TO-OUT
!
interface GigabitEthernet0/1
 zone-member security INSIDE
interface GigabitEthernet0/0
 zone-member security OUTSIDE
!
! Χωρίς zone-pair OUTSIDE->INSIDE το inbound απορρίπτεται by default,
! ενώ η επιστροφή για sessions με inspect (και τα ICMPv6 errors τους) περνά.
show policy-map type inspect zone-pair sessions
⚠ Παγιδα — Το Self Zone Ειναι Ανοιχτο Μεχρι να το Κλεισεις, και Τοτε Κλεινει και για το NDP

Η κίνηση προς τον ίδιο τον router ανήκει στο ενσωματωμένο zone self. Χωρίς zone-pair που να αφορά το self, η κίνηση του router επιτρέπεται, οπότε DHCPv6-PD, NDP και SSH δουλεύουν όλα. Τη στιγμή που προσθέτεις zone-pair OUTSIDE → self για να προστατέψεις το management, ό,τι δεν περνά ρητά από αυτό πετιέται, μαζί και το ICMPv6 και το DHCPv6 από τον ISP. Γράψε αυτή την πολιτική με βάση τη στήλη input του RFC 4890 πιο πάνω (ICMPv6, συν UDP 547→546 από fe80::/10) πριν από οτιδήποτε άλλο. Όπως με κάθε αλλαγή ZBF, έλεγξε τα v6 sessions στη δική σου έκδοση με την εντολή show πιο πάνω. Μη θεωρείς ότι ένα τεστ σε v4 καλύπτει και το v6.

04

Προστασια First-Hop

Το hop limit 255 εμποδίζει συσκευές εκτός link να μιλήσουν NDP. Δεν κάνει τίποτα για μια συσκευή συνδεδεμένη στο δικό σου switch.

Οποιοσδήποτε host σε ένα LAN segment μπορεί να στείλει Router Advertisements ή να απαντήσει σε DHCPv6. Συνήθως απλώς έχει λάθος ρύθμιση: ένα laptop με ενεργό Internet Sharing, ένα test VM σε bridge στο λάθος δίκτυο, ένας οικιακός router συνδεδεμένος ανάποδα. Οι hosts δέχονται το επιπλέον RA όπως είναι και αποκτούν δεύτερο default route. Το αποτέλεσμα πάει από «κάποιοι χρήστες δεν φτάνουν πουθενά» ως κίνηση που παίρνει σιωπηλά μια διαδρομή που δεν σχεδίασες. Η λύση ανήκει στο access switch, που ξέρει ποιες θύρες βλέπουν σε hosts:

Catalyst IOS-XE — RA guard και DHCPv6 guard στις θυρες των hosts
ipv6 nd raguard policy HOST-PORTS
 device-role host
ipv6 dhcp guard policy DHCP-CLIENTS
 device-role client
!
interface range GigabitEthernet1/0/1 - 46
 ipv6 nd raguard attach-policy HOST-PORTS
 ipv6 dhcp guard attach-policy DHCP-CLIENTS
! Τα uplinks προς τον router μένουν χωρίς policy ή με device-role router.
show ipv6 nd raguard policy HOST-PORTS
ΠλατφορμαΤι εχειςΤι κανεις
Cisco CatalystRA guard, DHCPv6 guard, ND inspection, source guardΤουλάχιστον RA + DHCPv6 guard σε κάθε θύρα host.
MikroTik RouterOSΔεν έχει RA guardΒάλε RA guard στο access switch αν το υποστηρίζει· client isolation στο Wi-Fi· ανίχνευσε rogue RAs (παρακάτω).
Wi-Fi APsClient isolationΤο isolation σταματά τα frames από host σε host, μαζί και ένα rogue RA, στο ίδιο SSID.

# τρέξ' το από host monitoring σε κάθε VLAN (cron, κάθε λίγα λεπτά)
rdisc6 -m eth0.10 | grep -c '^ from'     # -m: περίμενε όλους τους routers, όχι μόνο τον πρώτο

05

Αποδειξε την Ισοδυναμια Το δικο σου δικτυο

Ένα firewall που δεν έχεις δοκιμάσει από έξω είναι εικασία. Δοκίμασε και τις δύο οικογένειες από το ίδιο σημείο και σύγκρινέ τες.

Από ένα VPS που ελέγχεις, τρέξε το ίδιο scan στη διεύθυνση IPv4 και στη διεύθυνση IPv6 μερικών hosts που σου ανήκουν: το WAN του router, έναν server, έναν σταθμό εργασίας (με τη σταθερή διεύθυνσή του, όχι την temporary). Τα αποτελέσματα πρέπει να ταιριάζουν. Κάθε θύρα ανοιχτή στο v6 και φιλτραρισμένη στο v4 είναι κανόνας v6 που λείπει.

Κανε scan τους δικους σου hosts και στις δυο οικογενειες, μετα συγκρινε
$ nmap -Pn -p- --open -oG v4.txt 198.51.100.20
$ nmap -6 -Pn -p- --open -oG v6.txt 2001:db8:abcd:1220::20
$ diff <(grep -o '[0-9]*/open' v4.txt) <(grep -o '[0-9]*/open' v6.txt)
# κάθε γραμμή εδώ είναι ασυμφωνία πολιτικής v4/v6
Αποδειξε οτι δουλευει το PMTUD (το Packet Too Big περναει)
$ tracepath -6 www.example.com
 1?: [LOCALHOST]                        0.012ms pmtu 1500
 1:  2001:db8:abcd:1210::1              0.501ms
 2:  2001:db8:ffff:1::1                 6.884ms pmtu 1492    # το hop του PPPoE δηλώνει μικρότερο MTU
 ...
     Resume: pmtu 1492 hops 9 back 9
# Αν οι μεγάλες μεταφορές κολλάνε αλλά το tracepath δεν δείχνει ποτέ πτώση pmtu, κάτι
# ανάμεσα σε σένα και στην άλλη άκρη τρώει τον τύπο 2. Στο δικό σου edge, έλεγξε τη σειρά των κανόνων.

Βασικα Συμπερασματα

  1. Το RFC 4890 απαντά στο ερώτημα του ICMPv6 ανά τύπο και ανά κατεύθυνση. Τα errors 1–4 πρέπει να περνούν· NDP και MLD πρέπει να φτάνουν στον router· το router renumbering (138) όχι.
  2. Το established/related καλύπτει ήδη τα περισσότερα errors. Τα ρητά accepts ανά τύπο είναι για ροές που έχασε το conntrack.
  3. Γράφε την πολιτική v6 με interface lists, όχι με διευθύνσεις. Τα delegated prefixes αλλάζουν.
  4. Η ισοδυναμία περιλαμβάνει τους κανόνες μεταξύ VLAN. Αλλιώς η κατάτμηση υπάρχει μόνο στο v4.
  5. Οι πολιτικές self-zone του ZBF πρέπει να περνούν ICMPv6 και DHCPv6, αλλιώς χάνεις το NDP και το prefix σου τη στιγμή που προστατεύεις το management.
  6. Τα rogue RAs είναι θέμα του switch. RA guard και DHCPv6 guard όπου υπάρχουν, isolation στο Wi-Fi, και ανίχνευση παντού αλλού.
  7. Δοκίμασε από έξω και στις δύο οικογένειες και σύγκρινε. Έλεγξε το PMTUD με το tracepath.

Δεν εισαι σιγουρος οτι το v6 firewall ταιριαζει με το v4;

Ελέγχω την πολιτική edge και first-hop σε δίκτυα MikroTik και Cisco, τη δοκιμάζω από έξω και στις δύο οικογένειες διευθύνσεων, και κλείνω τα κενά ώστε το dual-stack να μη σημαίνει διπλή έκθεση.
