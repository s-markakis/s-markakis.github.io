Surgery on a Running Network
Cisco to MikroTik, Gradually

Swapping vendors tempts people into a big-bang weekend: rip out the Cisco, cable in the MikroTik, pray the config translation was complete. It rarely is, and the rollback is “put the old one back” at 3am. The calmer way treats the two vendors as a temporary mixed network: stand the new box beside the old, make them peers, and move the network across one subnet at a time, keeping both until nothing depends on the old.

Surgery Migration Cisco MikroTik VRRP OSPF

A vendor migration is not a config translation exercise — it is a live-network change where the two devices speak different dialects of the same protocols. The danger of the big-bang swap is that config translation is never perfect: a QoS policy, an ACL subtlety, a timer, a feature that does not map one-to-one. You find the gap after the old box is already unplugged.

The surgical approach runs both vendors in parallel as a temporary mixed network. They interoperate over the protocols that are standards — a trunk for VLANs, OSPF for routing, VRRP for the shared gateway (standards, unlike Cisco-only HSRP) — so traffic can flow through either while you migrate subnet by subnet. Each VLAN’s gateway moves from Cisco to MikroTik one at a time, provably reversible, and the WAN moves last. The old box leaves only when it is idle.

Two Vendors, Peered, Then One

The MikroTik joins beside the Cisco as an OSPF/VRRP peer; gateways move across one subnet at a time; the Cisco leaves when it carries nothing.

02

The Cutover, Subnet by Subnet

Peer over standards, migrate gateways with VRRP priority, move the WAN last — every step reversible by flipping a priority or a link.

StepDoRollback
1 · Parallel + trunkRack the MikroTik, trunk it to the Cisco carrying all VLANs. No gateways on it yet.Unplug the trunk.
2 · Peer the routingBring up OSPF between Cisco and MikroTik; verify both learn each other’s routes. Still no user traffic on the MikroTik.Shut the OSPF interface.
3 · Shared gateway (VRRP)For a pilot VLAN, add the MikroTik to a VRRP group as backup (Cisco master). The virtual IP is unchanged for hosts.Remove the MikroTik from the group.
4 · Flip the masterRaise the MikroTik’s VRRP priority so it becomes master for that VLAN. Sub-second, same virtual IP/MAC.Lower priority — Cisco resumes master.
5 · Repeat per VLANMigrate each subnet’s gateway the same way, pacing by risk.Per-VLAN priority flip.
6 · Move the WAN lastOnce all gateways are on the MikroTik, cut the internet uplink across; retire the Cisco when idle.Move the WAN back to the Cisco.
⚠ Gotcha — HSRP is Cisco-only; and the spanning-tree dialects differ

Two interop traps. Use VRRP, not HSRP, for the shared gateway — HSRP is Cisco-proprietary and the MikroTik cannot join it, whereas VRRP is a standard both speak. And the spanning-tree dialects are not identical: Cisco’s per-VLAN PVST+ and MikroTik’s (R)STP/MSTP interoperate only with care — agree on a common mode (MSTP or plain RSTP) and set the root deliberately, or the trunk between them can blackhole a VLAN or trigger a reconvergence. Feature idioms differ too (QoS, NAT, ACL vs firewall) — translate behaviour, then verify it, do not assume the config maps one-to-one.

Takeaways

  1. Run both vendors in parallel as a temporary mixed network — no big-bang weekend, no 3am rollback.
  2. Peer over standards — a VLAN trunk, OSPF for routing, VRRP for the shared gateway.
  3. Migrate gateways one VLAN at a time with a VRRP priority flip — sub-second, same virtual IP for hosts.
  4. Use VRRP, not HSRP — HSRP is Cisco-only and locks the MikroTik out of the group.
  5. Mind the spanning-tree dialects and translate feature behaviour, not config syntax — then verify. Move the WAN last.
