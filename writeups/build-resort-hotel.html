Build: The Resort
Hotel Network

A large resort hotel in Crete: reception, accounts, a mini market, three pools, a spa, a lobby, parking and a floor of guest rooms, with 44 access points between them. It starts from a real Packet Tracer file that had the cabling right and nothing else. This is how it becomes a network, bottom-up in twelve tested steps.

Cisco Hospitality WLC Guest Wi-Fi Dual WAN CME Packet Tracer

Hotels are a strange mix. Most of the traffic is guests you know nothing about, on Wi-Fi you're judged on. Next to that sit a property-management system (PMS) holding every booking, a till that takes cards, and an accounts office that pays the suppliers. All of it hangs off the same core. The design job is to make the guest side fast and disposable, and the rest of it out of reach.

This build is different from the others in the series: it starts from someone else's drawing. The Packet Tracer file had a sensible physical layout and every device at factory defaults. So before any config, there's a review: what the file got right, what would have stopped it working, and what was added. The finished Packet Tracer file is attached, configured.

What the File Had, and What It Was Missing

The layout was right. Every device was at factory defaults, and three things would have stopped it working at all.

The original file has a 2911 edge router behind a second 2911 standing in for the ISP, a 3560-24PS core, eight 2960-24TT access switches (one per area), 44 lightweight access points, five 7960 phones, four printers, five PCs and two servers. The physical design is sound: a star from one core, one switch per zone, the APs grouped by where they hang. That part stays.

03

Five Design Decisions

Each one closes a requirement. Everything else in the post is detail.

  1. Guest traffic never touches an access switch VLAN. The APs run in local mode and tunnel every client frame to the WLC over CAPWAP. Guest and staff Wi-Fi VLANs (100, 90) exist only on the core and the WLC trunk. The AP switches carry two VLANs: management and the AP VLAN. A guest can't be bridged onto anything in a pool closet.
  2. The core routes and enforces; the edge only translates. All inter-VLAN routing and every ACL live on CORE-SW. The edge router does NAT, the WANs and voice. One place to read the policy.
  3. Policy by source VLAN. Untrusted segments (guest, staff Wi-Fi, POS) get an inbound ACL that denies all private space after a short list of exceptions. Accounts is protected in the other direction. No ACL refers to a single PC.
  4. Failover decided by reachability, not link state. A fibre ONT that stays up while the ISP is down is the common case. IP SLA probes a target beyond ISP-A and moves the default route when it stops answering.
  5. Everything that could be a template is a template. Eight access switches share one config shape: same management, same unused-port handling, same uplink. Only the port map differs.

    ⚠ Gotcha — DHCP Snooping Breaks the Core's DHCP Server
    
With snooping on, a 2960 inserts option 82 into every client DHCP request but leaves giaddr empty, because it isn't a relay. An IOS DHCP server on the core sees option 82 with a zero giaddr and drops the request as malformed. Clients get nothing, and nothing logs it on the access switch. no ip dhcp snooping information option stops the insertion. The other fix is ip dhcp relay information trust-all on the core, which trusts more than you need.

  

  
✓ Checkpoint

    ⚠ Gotcha — The 2960-24TT Has No PoE
    
The file's access switches can't power anything. In Packet Tracer each LAP and phone gets its power adapter module (already fitted in the attached file). In the real building, these closets need PoE+ switches, and the budget matters. Twenty Wi-Fi 6 APs at 15–25 W each is more than some 24-port PoE switches can deliver. Check the switch's total PoE budget against the AP datasheet's worst-case draw, not its typical draw.

    ⚠ Gotcha — Prune Both Ends, and Agree on the Native VLAN
    
A trunk with allowed VLANs pruned on only one side still passes STP for the rest and wastes nothing visible, until a VLAN you thought was gone shows up in a closet. A native-VLAN mismatch is worse: CDP logs it, but untagged traffic quietly crosses between VLAN 999 on one side and whatever the other side uses. Every trunk here has the same allowed list and native 999 on both ends. The one exception is the WLC port in step 7, on purpose.

The device the original file was missing. Without it, 44 access points are 44 expensive paperweights.

  
▲ Show step 7 in the interactive topology · see what this step adds, and click any device for its config

  
WLC-01 sits on the core with one trunk. Its management interface is untagged, which is why that trunk's native VLAN is 80 and not 999. The APs in VLAN 80 find it by broadcast discovery on the same subnet. In the real build, with APs in more than one subnet, DHCP option 43 or a DNS entry for CISCO-CAPWAP-CONTROLLER does the job. Two dynamic interfaces map the SSIDs onto VLANs 90 and 100.

The Policy Matrix as ACLs

  
Four ACLs on the core implement the whole matrix from section 05.

  
▲ Show step 8 in the interactive topology · see what this step adds, and click any device for its config

  
Untrusted segments get an inbound ACL on their SVI: first the exceptions, then deny all private space, then permit the rest (the internet). Accounts is the reverse case: an outbound ACL on its SVI lets replies in and blocks anything internal starting a session.

  
CORE-SW — ACLs and where they're applied
interface Vlan30
 ! outbound on accounts: replies get in, nothing internal starts a session
 ip access-group TO-ACCOUNTING out
interface Vlan50
 ! policy applied inbound, at the untrusted VLAN's gateway
 ip access-group POS-IN in
interface Vlan90
 ip access-group STAFFWIFI-IN in
! nobody uses VLAN 1: its SVI stays shut
interface Vlan100
 ip access-group GUEST-IN in
! guests: DHCP, then no private space at all, then the internet
ip access-list extended GUEST-IN
 ! keep DHCP renewals working (they are unicast to the gateway)
 permit udp any any eq bootps
 ! then deny every private range
 deny ip any 10.0.0.0 0.255.255.255
 deny ip any 172.16.0.0 0.15.255.255
 deny ip any 192.168.0.0 0.0.255.255
 ! everything else is the internet
 permit ip any any
! staff Wi-Fi: printers and the PMS, nothing else internal
ip access-list extended STAFFWIFI-IN
 permit udp any any eq bootps
 permit ip 10.10.90.0 0.0.0.255 10.10.60.0 0.0.0.255
 permit ip 10.10.90.0 0.0.0.255 10.10.70.0 0.0.0.255
 deny ip any 10.0.0.0 0.255.255.255
 permit ip any any
! the till: HTTPS to the PMS, and the internet
ip access-list extended POS-IN
 permit udp any any eq bootps
 permit tcp 10.10.50.0 0.0.0.255 host 10.10.70.10 eq 443
 deny ip any 10.0.0.0 0.255.255.255
 permit ip any any
! accounts: replies only from inside; the internet as normal
ip access-list extended TO-ACCOUNTING
 ! TCP replies to sessions accounts opened
 permit tcp any any established
 permit icmp any any echo-reply
 ! anything internal starting a session to accounts
 deny ip 10.0.0.0 0.255.255.255 any

    ⚠ Gotcha — The First Line Keeps DHCP Alive
    
permit udp any any eq bootps sits above the deny for a reason. The first DHCP Discover is a broadcast and would pass anyway, but the renewal halfway through the lease is unicast to 10.10.100.1, which is private space. Without that line, guests get an address, and a few hours later every device in the hotel drops off Wi-Fi when its renewal fails. That ticket is impossible to reproduce on the day.

The Edge: WAN1 and NAT

  
One router, three interfaces, and NAT written for two WANs from the start, even while only one exists.

  
▲ Show step 9 in the interactive topology · see what this step adds, and click any device for its config

  
The edge knows the inside as one summary (10.10.0.0/16 via the core) and translates it to the WAN address. The NAT statement uses a route-map that matches the exit interface instead of a bare ACL. With one WAN that changes nothing. With two, it's the only way the same inside hosts get translated to whichever WAN they actually leave through.

  
EDGE-RTR — WAN1, inside, NAT
! role + location in every name, so a log line says which box
hostname EDGE-RTR
interface GigabitEthernet0/0

 ! NAT outside = a WAN

 no shutdown
interface GigabitEthernet0/1
 description LAN to CORE-SW
 ip address 10.255.0.1 255.255.255.252

! what gets translated: the whole hotel range
ip access-list standard NAT-INSIDE
 permit 10.10.0.0 0.0.255.255

ip route 0.0.0.0 0.0.0.0 203.0.113.1

The Backup WAN and Tracked Failover

  
Probe something beyond the ISP, pin the probe to the primary, and let a floating route do the rest.

  
▲ Show step 10 in the interactive topology · see what this step adds, and click any device for its config

  
IP SLA pings 4.2.2.2 out of Gi0/0 every 5 seconds. The primary default route only exists while the track is up. When it goes down, the floating route (administrative distance 10) takes over, and the second NAT route-map translates to 198.51.100.2.

  
EDGE-RTR — WAN2, IP SLA, tracked default
! swap step 9's plain default for the tracked one
no ip route 0.0.0.0 0.0.0.0 203.0.113.1
interface GigabitEthernet0/2
 description WAN2 to ISP-B (backup)
 ip address 198.51.100.2 255.255.255.252
 ! NAT outside = a WAN
 ip nat outside
 no shutdown
! the same for WAN2
route-map NAT-ISPB permit 10
 match ip address NAT-INSIDE
 match interface GigabitEthernet0/2
! PAT to WAN2's address
ip nat inside source route-map NAT-ISPB interface GigabitEthernet0/2 overload
! probe a host beyond ISP-A every 5 seconds
ip sla 1
 icmp-echo 4.2.2.2 source-interface GigabitEthernet0/0
 frequency 5
! start the probe now and run it forever
ip sla schedule 1 life forever start-time now
! up while the probe gets replies
track 1 ip sla 1 reachability
! primary default: exists only while track 1 is up
ip route 0.0.0.0 0.0.0.0 203.0.113.1 track 1
! floating backup default (AD 10): used only when the primary is gone
ip route 0.0.0.0 0.0.0.0 198.51.100.1 10
! pin the probe to ISP-A, or it succeeds via ISP-B and the WANs flap
ip route 4.2.2.2 255.255.255.255 203.0.113.1

  
ISP-B
! role + location in every name, so a log line says which box
hostname ISP-B

    ⚠ Gotcha — Pin the Probe, and Don't Probe What Users Need
    
Without ip route 4.2.2.2 255.255.255.255 203.0.113.1, the probe follows the default route. Once failover happens, that default goes out ISP-B, the probe succeeds through the backup, the track comes back up, and the router flaps between WANs every few seconds. The host route keeps the probe on ISP-A whatever the default does. The flip side: that /32 forces all traffic to 4.2.2.2 through ISP-A. So the probe target must be something users don't depend on, which is why it isn't INTERNET-SRV.

  

  
✓ Checkpoint — the failover drill
    
On ISP-A: interface Loopback0, shutdown. That's ISP-A's upstream failing while the fibre link stays up. Within ~15 s, show track 1 goes Down and show ip route static shows the default via 198.51.100.1. A PC pinging 8.8.8.8 loses a few packets and recovers through ISP-B. Existing NAT entries still point at the old WAN until they time out. clear ip nat translation * speeds that up during the drill. Bring Loopback0 back and traffic returns to ISP-A.

    ⚠ Gotcha — SSH Needs Keys the Config Doesn't Carry
    
transport input ssh only works once the device has an RSA key, and keys aren't part of the running-config. Run crypto key generate rsa modulus 2048 once on each device, then ip ssh version 2. Until then, SSH is refused and Telnet is already off, so the console is the only way in. That's safe, but surprising if you didn't expect it. The lab password in this post and in the file is Lab-ChangeMe-1. Change it before the file goes anywhere near real hardware.

The Attacker's View

  
What someone sitting on the guest Wi-Fi, or plugged into a wall port, can and can't do. Read it as a list of controls, and a list of what's still open.

  
    
    
  • Guest Wi-Fi. Routed straight to the internet. Every private range is denied at the core, and with peer-to-peer blocking on the WLAN, guests don't even see each other. The weak point is the shared PSK printed at reception. A portal with per-stay credentials is the real fix (step 7).
    • 
    
  • A free wall port. Shut down and in VLAN 999. An enabled one only offers its access VLAN, because trunks are hard-coded with nonegotiate and a native VLAN nothing uses, so double-tagging lands nowhere.
    • 
    
  • A rogue DHCP server or a switch from home. Snooping drops the offers. BPDU guard err-disables the port the moment the switch sends a BPDU. The core is root on every VLAN, so even an unguarded port couldn't take over.
    • 
    
  • The till. One way in (HTTPS to the PMS) and one way out (the internet). That's why the PCI scope is one switch and one VLAN, not the whole hotel.
    • 
    
  • Still open, and worth closing next. Staff VLAN 20 can reach switch management SVIs. Add an access-class on the VTY lines that allows only an admin subnet. Accounts reaching the internet without filtering is the usual phishing path. DNS filtering at the edge would help. And the PMS has no backup in this design.
    •
