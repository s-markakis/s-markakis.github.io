MikroTik Lab
Το Σπασμενο Δικτυο

Το να κάνεις config είναι εύκολο· το να διορθώνεις το χάλι κάποιου άλλου στις 2 το πρωί είναι η πραγματική δουλειά. Αυτό το lab φυτεύει επτά ρεαλιστικά σφάλματα σε ένα δίκτυο RouterOS και σου τα δίνει σαν support tickets — τα ακριβή bugs που επαναλαμβάνονται σε πραγματικά sites MikroTik, και την εντολή διάγνωσης που βρίσκει το καθένα. Το δίδυμο του lab σπασμένου campus της Cisco.

MikroTik RouterOS Troubleshooting Lab Diagnostics

Κάθε σφάλμα παρακάτω είναι ένα που πραγματικά έχω διορθώσει σε ζωντανό box RouterOS, ντυμένο σαν ticket. Η αξία δεν είναι η απάντηση — είναι η μέθοδος: ένα σύμπτωμα δείχνει ένα layer, και μία στοχευμένη εντολή το επιβεβαιώνει ή το ξεκαθαρίζει. Δούλεψε bottom-up (link → L2 → L3 → NAT/firewall → routing) και συγκλίνεις γρήγορα· μάντεψε τυχαία και θα είσαι εκεί όλη νύχτα. Χτίσε το δίκτυο από τα προηγούμενα labs, βάλε έναν συνάδελφο να το σπάσει, μετά δούλεψε αυτά.

Το επαναλαμβανόμενο θέμα ειδικά στο MikroTik: το bridge κάνει τα περισσότερα L2 δουλειά και έχει μη προφανείς κανόνες (VLAN filtering, PVID, hardware offload), και το μοντέλο connection-tracking / routing-mark πίσω από το NAT και το policy routing κρύβει state που πρέπει να σκεφτείς. Αυτές είναι οι ίδιες κατηγορίες που φυτεύει το lab σπασμένου campus της Cisco, εκφρασμένες στα ιδιώματα του RouterOS.

Προαπαιτουμενα
  • Άνεση σε όλη τη σειρά — VLANs, DHCP/NAT, firewall, OSPF
  • Ένα lab που μπορείς να σπάσεις με ασφάλεια (ποτέ μην εξασκείσαι σε production)

01

Ticket #1 — "Το VLAN Επισκεπτων Δεν Εχει Δικτυο"

Οι επισκέπτες δεν παίρνουν DHCP και δεν μπορούν να κάνουν ping το gateway· τα άλλα VLANs είναι εντάξει. Μυρίζει Layer 2 σε αυτό το ένα VLAN.

RouterOS 7 — ελεγξε τον πινακα VLAN του bridge 
> /interface bridge vlan print
 vlan-ids=20  bridge=bridge  tagged=ether1  untagged=   # η θύρα access επισκεπτών ΛΕΙΠΕΙ
# Ρίζα του προβλήματος: η θύρα access επισκεπτών δεν προστέθηκε ποτέ στη λίστα untagged
# του VLAN 20 (και/ή το PVID της δεν είναι 20). Με vlan-filtering=yes το bridge κάνει drop
# frames σε θύρα που δεν είναι στη λίστα μελών του VLAN.
> /interface bridge vlan set [find vlan-ids=20] untagged=ether5
> /interface bridge port set [find interface=ether5] pvid=20

02

Ticket #2 — "Ενα VLAN Φτανει το Internet, τα Αλλα Οχι"

Το προσωπικό κάνει browse κανονικά· το νέο VLAN πωλήσεων παίρνει lease DHCP και μπορεί να κάνει ping τον router αλλά όχι το internet. Κλασικό scope NAT.

RouterOS 7 — επιθεωρησε τον κανονα masquerade 
> /ip firewall nat print
 chain=srcnat action=masquerade src-address=10.10.0.0/24 out-interface-list=WAN
# Ρίζα του προβλήματος: το masquerade έχει scope σε ΕΝΑ subnet (10.10.0.0/24), όχι το
# subnet πωλήσεων (10.10.30.0/24). Παλιός κανόνας copy-paste που δεν γενικεύτηκε ποτέ.
> /ip firewall nat set [find action=masquerade] src-address=""
# Καλύτερα: κάνε masquerade με out-interface-list=WAN για κάθε εσωτερική πηγή.

03

Ticket #3 — "Το Link OSPF Δεν Ανεβαινει"

Δύο routers, καλωδιωμένοι και με ping ανάμεσά τους, αλλά ο γείτονας OSPF δεν φτάνει ποτέ σε Full — κάθεται σε Exchange/Loading. Η υπογραφή ενός συγκεκριμένου σφάλματος.

RouterOS 7 — ο ελεγχος MTU 
> /routing ospf neighbor print
 state=Exchange ...                 # κολλημένο εδώ = σχεδόν πάντα MTU
> /interface ethernet print where name=ether2   # mtu=1480 στη μία πλευρά, 1500 στην άλλη
# Ρίζα του προβλήματος: MTU mismatch. Το OSPF ανταλλάσσει πακέτα DBD που περιλαμβάνουν το
# MTU· ένα mismatch παγώνει το adjacency σε Exchange. Ταίριαξε και τα δύο άκρα.
> /interface ethernet set ether2 mtu=1500

04

Ticket #4 — "Το DHCP Σταματησε να Δουλευει Μετα απο μια 'Μικρη Αλλαγη'"

Κανένας client δεν παίρνει διεύθυνση. Κάποιος "τακτοποίησε" το bridge χθες. Ο server υπάρχει και είναι ενεργοποιημένος — άρα είναι δεμένος λάθος.

RouterOS 7 — που ειναι δεμενος ο server; 
> /ip dhcp-server print
 name=LAN-DHCP interface=ether2 ...   # δεμένος σε ΦΥΣΙΚΗ θύρα, όχι το bridge
# Ρίζα του προβλήματος: το LAN μετακινήθηκε μέσα σε ένα bridge, αλλά ο server DHCP παραμένει
# δεμένος στο ether2. Οι clients ζουν στο broadcast domain του bridge· ο server
# σε μία μόνο θύρα δεν ακούει πια τα DISCOVER τους.
> /ip dhcp-server set LAN-DHCP interface=bridge

05

Ticket #5 — "Ενας Κανονας Firewall που Προσθεσα Δεν Κανει Τιποτα"

Ένας νέος κανόνας για να μπλοκάρει το internet ενός host είναι στη θέση του αλλά ο host συνεχίζει να κάνει browse. Ο κανόνας φαίνεται σωστός μεμονωμένα — άρα είναι θέμα σειράς ή fast-path.

RouterOS 7 — counters & FastTrack 
> /ip firewall filter print stats
 0 chain=forward action=fasttrack-connection connection-state=established,related
 ...
 8 chain=forward action=drop src-address=10.10.0.66  bytes=0   # ποτέ δεν χτυπήθηκε
# Ρίζα του προβλήματος: ένας κανόνας fasttrack παραπάνω στέλνει established/related flows κάτω στο
# fast path, παρακάμπτοντας μεταγενέστερους κανόνες. Οι υπάρχουσες συνδέσεις του host παρακάμπτουν το
# drop. Βάλε το drop ΠΑΝΩ από το fasttrack, και κάνε flush τις συνδέσεις του host.
> /ip firewall connection remove [find src-address~"10.10.0.66"]

06

Ticket #6 — "Το Dual-WAN 'Δουλευει' Αλλα τα Sites Σπανε Τυχαια"

Policy-routed dual-WAN, αλλά κάποια sessions αποτυγχάνουν περιοδικά — logins αναπηδούν, downloads κάνουν reset. Η υπογραφή ενός flow που φεύγει από δύο paths.

RouterOS 7 — πως εφαρμοζεται το mark; 
> /ip firewall mangle print
 chain=prerouting action=mark-routing new-routing-mark=via-B protocol=tcp dst-port=443
# Ρίζα του προβλήματος: το routing-mark εφαρμόζεται ΑΝΑ ΠΑΚΕΤΟ σε ένα match, χωρίς
# connection-mark. Πακέτα return/άλλα της ίδιας ροής χάνουν το match και
# παίρνουν το άλλο WAN -> ασύμμετρο, το stateful NAT σπάει. Κάνε mark τη ΣΥΝΔΕΣΗ
# πρώτα, μετά προέκυψε το routing-mark από αυτήν (δες το post policy-routing).

07

Ticket #7 — "Το Switch Ειναι Κολλημενο στο 100% CPU" Ασφαλες να Τρεξεις

Το throughput κατέρρευσε και το CPU είναι στο μέγιστο σε ένα box που έκανε switch σε line rate. Κάτι απενεργοποίησε το hardware offload.

RouterOS 7 — ελεγξε τη σημαια offload 
> /interface bridge port print
 #   INTERFACE  BRIDGE  HW  ...
 0   ether2     bridge  no    # H(ardware) offload OFF — η κίνηση χτυπά το CPU
> /interface bridge print
 dhcp-snooping=yes ...          # ρίζα του προβλήματος: η ενεργοποίηση snooping έριξε το offload σε αυτό το chip
# Διόρθωση: απόφασε ανά box — κράτα το snooping και δέξου CPU switching σε έναν μικρό
# router, ή απενεργοποίησε το feature που κοστίζει offload σε ένα core υψηλού throughput.

Βασικα Συμπερασματα

  1. Δούλεψε bottom-up — link → L2 (bridge/VLAN) → L3 → NAT/firewall → routing. Ένα σύμπτωμα ονομάζει ένα layer· μία εντολή το επιβεβαιώνει.
  2. Σφάλματα VLAN στο bridge (λείπον μέλος, λάθος PVID) είναι η αιτία #1 για "ένα VLAN είναι νεκρό" — διάβασε το /interface bridge vlan print.
  3. OSPF κολλημένο σε Exchange/Loading = MTU mismatch, σχεδόν πάντα.
  4. DHCP δεμένο σε θύρα αντί για το bridge είναι το κλασικό bug "σταμάτησε μετά από μια αλλαγή".
  5. Το FastTrack παρακάμπτει μεταγενέστερους κανόνες — ένα νέο filter που "δεν κάνει τίποτα" είναι συχνά flows που το παρακάμπτουν στο fast path· έλεγξε counters και κάνε flush συνδέσεις.
  6. Routing-marks ανά πακέτο σπάνε flows σε πολλά WANs — κάνε πάντα mark τη σύνδεση πρώτα. Και η ενεργοποίηση features του bridge μπορεί να σκοτώσει το hardware offload — παρακολούθα τη σημαία H όταν το CPU ανεβαίνει.
